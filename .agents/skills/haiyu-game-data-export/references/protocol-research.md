# 协议取证：先确定事实，再设计增删改

## 1. 证据来源与定位

先定位以下内容，读取适用的约束文件：

- Haiyu `src/Extensions/Haiyu.ABI/Protocol/WavesGameData.proto`：字段号、类型、repeated/map、可选消息结构。
- 同目录 `WavesMessageIds.cs`：编号常量。相似名称不是相同消息。
- `Services/GameDataExport/Protocol/ProtocolCatalog.cs` 及其资源：实际解码使用的元数据。
- 客户端对应版本的 controller/model/data：注册、发送请求、响应回调、实际合并行为。
- 需要静态配置时再定位数据仓库的实际分支与提交。配置描述奖励/名称，不自动表示玩家已经获得它。
- 用户真实 JSONL、capture-index、manifest：本次实际出现的载荷和顺序。

参考源码可能位于相邻 WutheringMod 的 `DecompiledSource/Aki.Game`，但不要假定路径或提交永远如此。此目录是只读参考，不在那里修改游戏文件或放临时脚本。

从关键词和调用方双向搜索，使用 `rg`；命中太多就缩小文件/方法或落到仓库外日志分段读。**被截断的搜索结果不能证明“没有其他消息”。**

常用命令形状，方括号内容需替换后才执行：

```text
rg -n "[业务名]|[消息名]" src/Extensions/Haiyu.ABI/Protocol/WavesGameData.proto
rg -n "[消息名]" src/Extensions/Haiyu.ABI/Protocol/WavesMessageIds.cs
rg -n "[消息名]|[回调名]" [参考源码目录]
git -C [参考仓库] rev-parse HEAD
```

不要为业务接入重新生成所有协议。仅当协议缺失或版本失配有证据时，先读 `tools/WavesProtocolGenerator/README.md`，按现有生成流程处理并审查生成差异；不手改 obj 中的生成 C#。

## 2. 每种消息都填这张表

工作表中至少一行对应一种语义不同的消息。`待确认` 不是可以省略的空格。

| 内容 | 必须记录的事实 |
|---|---|
| 身份 | 消息名/ID、对象键字段及类型，配置 ID 与实例 ID 分开 |
| 触发 | 登录推送、UI 查询、操作响应、主动通知、试用/预览或机器人 |
| 成功条件 | 错误码字段号，缺省错误码值，整体成功还是成功子集 |
| 数据字段 | 编号、类型、单位；嵌套对象与 repeated/map 的含义 |
| 全量 | 是否 Clear；分页/批次/总数/完结证据；首次与后续是否不同 |
| 修改 | 完整覆盖、逐字段/逐键 patch、绝对数量还是差值 |
| 删除 | 单删、成功子集、全量替换时缺席删除、时间到期仅本地显示变化 |
| 重复 | 重复事件和重复键分别怎么处理；后值覆盖还是冲突 |
| 缺省 | 0、false、空字符串、空列表、缺失子对象分别是什么意思 |
| 顺序 | 主体、子对象、关系、技能、激活的真实先后顺序 |
| 恢复 | 哪个消息能证明完整性，能否只补齐一个实体 |
| 证据 | 仓库提交、文件/方法、可复核的载荷或匿名回归向量 |

## 3. 从客户端操作推断合并规则

以下是**搜索线索**，不是不看上下文的自动判定器：

| 客户端实现 | 候选语义 | 仍要确认 |
|---|---|---|
| Clear 后逐项添加 | 完整替换 | 是否只是本地某个缓存或一次查询的结果 |
| `dict[key] = value` | 按键 upsert，后值覆盖 | 值是完整实体，还是仅某个字段 |
| `TryAdd` / 目标已存在直接返回 | 新增去重 | 是否确实是服务器通知的业务处理路径 |
| 遍历列表，不 Clear | 合并，不凭缺席删除 | 首次列表能否作为登录基线，有无分页 |
| 清空 base/add 列表，再逐键赋值 | 整组属性替换 | 同条消息中的重复键往往合法，后值覆盖 |
| 针对一个技能调用 SetSkillLevel | 单技能 patch | 不应清空其他技能 |
| Remove/删除成功 ID 列表 | 显式删除 | 部分失败、重复删除、是否级联清理关系 |
| 成功后没有状态更新，只展示奖励/提示 | 可能只是 ACK | 真正事实是否来自另一条 Notify |
| 查配置并懒创建条目 | 有证据的新增/更新合并 | 不能误判所有未知 ID 为丢包 |
| 目标为 null 时不操作，稍后完整 Activate | 初始化先行的可能性 | 查真实顺序；不能仅靠孤立 null 判断忽略所有目标缺失 |

同一个 roleInfo 中，技能列表可能逐键合并，属性列表却整体替换，技能节点又完整替换。不能给整个对象套一个“所有数组都是全量”规则。

## 4. 最容易误判的载荷

### repeated 不保证唯一

protobuf 的 repeated 本来就允许重复。真实角色 baseProp 中会出现重复 ID，客户端按字典赋值。应复现客户端的后值覆盖；节点列表若客户端使用 Dictionary.Add，则重复 ID 可能反而应该拒绝。分别取证，不能全局去重或全局拒绝。

### proto3 缺省值不等于字段无变化

整数零、false、空列表可能就是新状态。不要用 `if(value != 0)` 跳过更新。若业务要区分“缺席”和“显式零”，必须检查协议是否有 presence、oneof、可选子消息或独立 patch 掩码，不能用普通标量臆造 presence。

缺失一个可选消息对象与它存在但内部值全零也不同。`RoleSkillQuickLevelUpResponse` 的成功回调允许 RoleInfo 缺席；这种 ACK 不应该先创建一个 Required 来源再报缺少基线。

### 成功 map 的值不一定是错误码

邮件 `successIdMap` 的值为该封邮件的新状态位。只更新成功集合；不能将值 3 当成错误码，也不能修改没有成功的其他请求目标。其他业务可能采用不同语义，重新查其回调。

### 请求上下文不能凭空补齐

如果成功响应只有 errorCode，没有目标或新值，查随后是否有权威通知。若必须依赖请求上下文而现有管线只有下行，记录限制；保留同步保护或扩大已授权的调研，不能猜目标、更不能擅自主动发请求。

### 预览与拥有关系

技能升级预览不是当前技能等级。角色展示列表、试用机器人、联机他人面板不是账号拥有角色集合。属性查询可能返回机器人 ID；“收到属性”不自动意味着拥有该角色。

### 初始化顺序

已观察到：新角色属性/节点/技能先于完整 Active。未知目标有三种不同解释：

1. 查询/试用数据：按客户端语义排除，不创建拥有关系。
2. 已有来源基线，实体正在初始化：软等待完整对象，期间不输出假完整快照。
3. 无基线或真正损坏/遗漏：硬失同步，等待可靠完整恢复。

不要为了支持情况 2，直接把情况 3 也放行。

## 5. 状态派生与配置

- 保存服务端原始事实，再派生展示字段。位掩码应按完整返回状态解释，未知位保留。
- 邮件已读、附件领取、收藏独立；没有附件时不是“未领取”。领取不能直接再次增加背包数量。
- 成就完成时间、是否领奖、进度独立；进度达到总数不能自动表示完成或领取。
- 属性保持原始单位，除非确认配置、公式和缩放。当前角色同 ID base+add 的合计不能再重复叠加声骸贡献，也不等同战斗 buff 面板。
- 配置奖励表能补充“该成就奖励什么”，不能补造“本账号已经领取了什么”。配置版本需要与游戏版本对应。
- 可检验约束如五槽、等级范围不能用来静默截断或夹值。保留异常原值并标记，或者按经证明规则拒绝并保留旧文件。

## 6. 证据不够时怎样继续

把事实与假设分开写。例如：“首次登录列表观察到 19 个角色；客户端后续按角色合并；协议无总数/分页标记，因此不能仅凭名字断言任意后续 Notify 都是完整替换。”

若用户未提供实测数据，构造**匿名、独立、能推翻假设**的测试向量，并明确真实顺序尚待实测；不得伪称已抓包验证。若缺少必要协议，先定位可用来源，再提出一个具体问题，而不是请用户替你设计整套方案。
