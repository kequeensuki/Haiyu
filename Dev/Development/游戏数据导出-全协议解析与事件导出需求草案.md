# 游戏数据导出：全协议解析与事件导出需求草案

日期：2026-11-05。状态：已按确认的首期范围实施；Windows 实机验证由用户执行，步骤与标准见《全协议事件导出-实施与Windows验收》。本文保留最初需求与调研基线。

## 1. 已确认目标与范围

将现有背包导出能力扩展为：从指定版本的游戏反编译 C# 源码生成完整协议定义及消息注册表，对实际捕获到的服务端下行消息进行通用解析，按玩家保存可追溯的消息事件。

用户已确认：

1. 覆盖全部服务端下行消息，不限 `Notify` 后缀，包括实际下行的 `Response`、`Push` 以及其他消息。
2. 首期完成完整协议生成、通用解析、消息事件导出；保留现有背包快照。其他业务数据的状态合成后续按模块实现。

“完整”的边界：覆盖本版本源码可确定的协议定义；“导出全部”的边界：导出捕获期间实际收到、能够完整重组的服务端消息。不能据此保证获取服务器未发送的数据、捕获前的历史消息或游戏的全部业务状态。

本期的下行消息限定在既有 UDP/KCP 网关链路中承载的游戏协议，不包含 HTTP 资源下载等其他通道。只做被动捕获，不主动构造请求或补发查询。客户端上行消息不纳入首期导出范围。

## 4. 协议生成要求

### 4.1 输入与可复现性

- 输入为显式指定的 WutheringMod 仓库 / 源码目录及协议基线；路径由参数传入，不能依赖开发者机器的绝对路径。
- 输入只读，不改游戏源码，不执行游戏代码，不要求启动游戏。
- Haiyu 正常构建使用已提交的生成产物，不要求另一仓库与特定本机目录同时存在。
- 支持生成及只检查差异的模式；同一基线重复生成内容一致。生成时间等非确定信息不影响校验。
- 全部分析和校验完成后再替换正式产物；失败保留上一套可用协议，不能留下半套 schema 和注册表。

### 4.2 还原规则

必须恢复：

- message、引用依赖、空消息、枚举、嵌套类型和限定类型名。
- 字段号、protobuf 标量类型、repeated、map、oneof、实际存在的字段 presence 语义。
- `int32/int64` 与 `sint32/sint64`、`fixed32/fixed64`、`sfixed32/sfixed64` 的区别。
- 枚举数值、负值及别名；repeated packed 编码和实际默认 / 存在性行为。

字段常量和 C# 属性只是线索，必须结合 `FieldCodec`、读写方法及 tag 验证。不能仅用属性类型或一组正则猜测全部协议；也不能把 oneof 生成的 `HasXxx` 一概误认为普通 optional 字段。

生成器须建立带依赖关系的结构模型，再输出 proto 与注册表。名称冲突、protobuf 关键字、顶层枚举值作用域冲突应采用确定且可追踪的映射，不改变字段号和枚举数值。现有背包消费代码的类型 / 属性变化须迁移并回归验证。

目标是可证明的 wire 兼容，不承诺逐字恢复原始 `.proto` 文本、注释和已被裁剪的 option。无法确定原始字段拼写时，输出稳定命名并记录映射，不伪称原始名称。

未知类型、缺失依赖、编号冲突、证据矛盾或不可还原的编码必须进入带文件 / 类型 / 字段定位的阻断清单。不能静默跳过，也不能随意降级成 int32 或 bytes 后宣称全量完成。

### 4.3 msgId 注册表

- 由 `EMessageId`、`NetMessage` 标记及 `NetDefine` 工厂交叉验证；不能推导“相邻编号就是请求与响应”。
- 首期 schema / 注册表覆盖当前已知协议及其完整依赖，包含双向类型；运行期只导出实际下行消息。
- 多个编号合法指向同一类型须保留；重复编号冲突必须报告。
- 使用静态生成的 parser / 工厂；不在运行期扫描官方程序集、动态加载 DLL 或按类型名查找 parser。

## 5. 通用解析链路与分层

建议数据流：

`捕获 → 按连接重组 / 切帧 → 解密解压 → 玩家上下文 / 通用解析 → 事件写入`

同时将现有背包消息交给原有快照模块；两个消费者共享验证后的消息，不重复维护传输、握手或会话密钥逻辑。

职责边界：

- 生成工具：源码分析、协议、注册表、版本报告。
- 捕获 / 会话层：网卡、传输重组、密钥、玩家身份及连接生命周期。
- 通用解析层：按注册表将明文载荷解析为类型化 protobuf，返回结构化状态。
- 事件导出层：组织事件、归属玩家、流式写入、分片和统计。
- 背包快照层：维持现有四类背包及业务完成判定。
- UI / ViewModel：模式选择、文件位置、状态和计数展示，不解析 proto、不持有全部消息、不直接写事件文件。

帧方向由连接端点与实际收包方向确定，不通过消息名称后缀筛选。Exception 等没有 msgId 的帧按控制事件记录，不捏造消息编号或使用错误 parser。

泛化 protobuf 的 JSON 输出也必须验证 NativeAOT 兼容；不能直接假定 `JsonSerializer.Serialize(IMessage)` 或 protobuf JSON formatter 在裁剪后自动可用。可选择静态生成的 JSON 写入器，或经过 NativeAOT 实测的描述符访问方案。

## 6. 事件格式与玩家归属

### 6.1 保存模型

新增“全部服务端消息”导出模式，建议默认仍为现有背包模式，用户显式选择全量；现有背包导出行为和文件格式保持兼容。全量模式下保留背包快照，同时追加消息事件，不把事件重新合成一个不断扩大的 JSON 对象。

建议格式为 UTF-8 JSONL，每行一个事件。每个事件至少包含：

| 字段 | 含义 |
|---|---|
| captureId / eventIndex | 本次捕获标识及本地接收序号 |
| receivedAt | 接收时间，含时区信息 |
| sessionId / connectionId | 登录会话标识和传输连接标识，二者分开 |
| playerId | 已确认的玩家，未确认时为 null |
| direction / frameType | 实际方向及帧类型 |
| msgId / messageType | 原编号及原限定类型名，无法确定时为 null |
| seqNo / rpcId | 原帧序号及 RPC 关联信息（如有） |
| schemaVersion / decodeStatus | 协议基线及解析状态 |
| payload | 成功解析的完整 protobuf 数据 |
| rawPayload / error | 未解析载荷的 Base64 和结构化错误（适用时） |

序号代表本地观察顺序，不伪称跨连接的服务器全局顺序。JSON 数值遵循明确、稳定的 protobuf 映射，尤其不能把 int64/uint64 经 double 转换而丢精度；bytes、未知枚举值和缺省字段行为需有固定规范和测试。

新事件不额外附带 RSA 私钥或解密上下文里的明文会话密钥。

### 6.2 未知和失败消息

- 未知 msgId、已知类型解析失败、密钥尚未取得、无法解密或无法完整重组，应分别统计，不能都当“没有数据”。
- 能确定完整载荷但无法解释时，保留原始字节及处理阶段；密文与明文不可混淆标记。
- 已解析消息存在未知字段时标记，并保留足以日后重新解析的原始 protobuf。不能因解析器接受未知字段就声称所有字段已知。
- 对完整已知消息是否额外保留原始载荷可作为诊断选项；不要对所有成功消息强制重复存储一份 Base64。
- 对不完整传输不能捏造“完整 protobuf”；记录明确的重组缺口 / 损失状态。
- 普通未知或解析失败的消息不应终止其他消息的导出；会话基础信息和资源不可恢复的故障仍须明确结束并返回原因。

### 6.3 账号与网络生命周期

- captureId 标识一次开始至停止的捕获；同一捕获中可含多个玩家及多次登录。
- 登录会话与 KCP / 网络连接分开标识。仅切网或传输重连，不重置已有玩家上下文和统计。
- 新登录 / 换钥后、身份重新确认前的消息不能自动归给上一个玩家。协议实现必须给出有源码依据的边界规则。
- playerId 尚未取得时先保存为“待归属”，不无限缓存于内存，也不创建伪造的 playerId=0 目录。确认身份后用会话绑定索引关联早期事件；无法确认就保持未归属，不猜测。
- 同一玩家重复下发的合法消息逐次保留；只能去除有传输 / 帧身份依据的重传和多接口重复捕获，不能按消息体内容相同去重。

### 6.4 文件组织建议

在现有 `GameDataExport` 下增加捕获索引及玩家事件目录，例如：

```text
GameDataExport/
  captures/{captureId}/manifest.json
  captures/{captureId}/unresolved-000001.jsonl
  {playerId}/game-data-{原有时间戳}.json
  {playerId}/captures/{captureId}/events-000001.jsonl
```

manifest 记录协议版本、玩家 / 会话绑定、分片路径、解析统计、错误、结束原因和完整性状态。文件名包含足够唯一的捕获标识，不能仅依赖秒级时间戳防冲突。未归属事件后续可经索引关联，避免反复搬写大文件。

## 7. 持续导出、UI 与现有功能兼容

- 流式写入；有界队列、有界内存和文件分片，不能随捕获时长线性增长内存。
- 在实施时用真实流量基准确定队列、分片大小、磁盘总量限制和刷新周期，并记录默认值及压力测试结果。
- 不能静默丢弃：队列溢出或磁盘达到上限，建议默认受控结束全量捕获，保存已写结果并明确告知是否有缺失。不得覆盖旧分片冒充完整导出。
- 磁盘失败与 JSON 序列化失败需有可定位状态；不能阻塞 UI 或吞掉错误继续显示成功。
- 停止时关闭接口、排空已接收队列并刷新文件 / manifest；退出或崩溃后可以识别未完成捕获。JSONL 尾部半条记录应可被检测和恢复到最后一条完整记录。
- UI 按固定间隔刷新聚合统计，不逐消息渲染或向窗口堆积全部事件。
- 显示已接收、解析成功、未知协议、解析失败、待归属数量，以及导出文件位置。计数单位必须明确，不能混用 UDP 帧、protobuf 消息和快照更新次数。
- 按玩家显示本次捕获的事件统计及现有快照更新次数；结束汇总包含所有玩家，重复打开窗口不丢汇总。
- 保持既有网卡选择 / 切网恢复、30 分钟等待初始密钥超时、退出自动停止、切号隔离、凭据读取及背包导出回归行为。

## 8. 版本维护与验证标准

每次游戏协议更新都执行生成和差异检查：新增 / 删除 / 重命名类型、msgId 变化、字段号和编码变化、枚举数值变化必须可审查。proto、注册表、版本清单作为同一套产物更新。

不能仅以“编译成功”证明协议正确：protobuf 对不匹配 schema 也可能接受并保留为未知字段。

验收至少包含：

1. 源码盘点覆盖率、依赖闭包、注册表三方一致，未解决阻断项为 0。不能只以当前 3910 为永远不变的硬编码断言。
2. protoc 检查及 .NET 编译通过；Windows NativeAOT 发布和实际通用解析 / JSON 导出通过，报告全量后的构建时间、产物大小、启动及运行资源变化。
3. 使用独立来源的序列化字节 / 已有可信回放核对字段值、presence、oneof 和编码。优先与同版本官方序列化器对照；若无可运行程序集，明确证明范围，不能把生成器与自身往返当成等价性证明。
4. 覆盖普通标量、zigzag、fixed/sfixed、map、packed、嵌套、enum、oneof、空消息和未知字段，以及实际下行的 Response / Notify / Push。
5. 覆盖分片、重传、多接口重复、压缩、换钥、切网、切号及 playerId 未确认窗口；不同玩家不得串数据，不漏掉相同内容但身份不同的事件。
6. 未知编号、协议版本不匹配、损坏载荷、磁盘满、队列满、强制退出可诊断，文件可读，统计不伪报成功。
7. 所有既有背包、玩家独立更新次数和多玩家结束汇总回归通过。

不要求为所有消息逐个设计业务场景；要求全量结构校验、代表性编码验证，以及真实回放覆盖报告，明确“已知可解析类型”和“实测收到的消息”的区别。

## 9. 实施阶段与首期非目标

| 阶段 | 内容 | 验收关口 |
|---|---|---|
| M1 | 全量源码建模、proto / 注册表 / 版本报告生成 | 无静默遗漏，依赖完整，protoc 通过 |
| M2 | 全量编译、NativeAOT 通用解析与 JSON 可行性 | 不依赖动态加载官方 DLL，编码验证通过，资源影响可接受 |
| M3 | 事件流写入、玩家归属、分片 / manifest 与 UI 接入 | 持续捕获、账号隔离、异常退出及结束汇总通过 |
